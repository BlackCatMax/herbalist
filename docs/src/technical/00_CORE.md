# Herbalist — Полная математическая модель (Technical Specification v2.3 — UPDATED CORE)

Документ содержит **полную спецификацию** с разметкой:

* 🔒 **CORE** — неизменяемое математическое ядро
* ⚙️ **SEMI** — параметры, доступные для балансировки
* 🧪 **OPEN** — свободно изменяемая часть (контент, визуализация)

Версия 2.3 включает финальные уточнения:

* **Meta Coupling** с snapshot-семантикой (одновременное обновление из исходного состояния)
* **Каноническое определение smoothstep** в CORE
* **Разделение S_real / S_perceived**
* **Гибридная модель состояния (direction + magnitude)**
* **Замкнутый pipeline мира**

---

## 🔒 1. Общие принципы (CORE)

Система описывает трансформацию состояния через **приращения (Δ)** в рамках замкнутого цикла мира.

---

## 🔒 1.1 Представление состояния (CORE)

Состояние системы задаётся как:

```text
S_real(x, y, t) = (d, m)
```

где:

* `d = (body, mind, spirit, nature)` — **нормированный вектор направления**, `|d| = 1`
* `m` — **скаляр величины (magnitude)**, `m ∈ [0, M_max]`

---

### Интерпретация

* `d` определяет **качественный профиль состояния**
* `m` определяет **интенсивность / насыщенность состояния**

---

## 🔒 1.2 Восприятие (CORE)

Игрок не взаимодействует с `S_real` напрямую.

Все взаимодействия происходят через:

```text
S_perceived = Distort(S_real, Morok)
```

---

### Инвариант

```text
All Player Actions = f(S_perceived)
```

---

## 🔒 1.3 Pipeline системы (CORE)

Единственный допустимый поток изменений:

```text
S_real
→ Distort(Morok)
→ S_perceived
→ Player Action
→ Intent_player
→ Intent_system
→ ΔS
→ S_real'
→ (Perception)
```

---

## 🔒 1.4 Намерение (CORE)

Система различает два типа намерения:

```text
Intent_player = F(Action(S_perceived))
Intent_system = F(Action(S_real))
```

---

### Следствие

```text
ΔIntent = Distance(Intent_player, Intent_system)
```

---

👉 Это фундаментальный источник:

* ошибок
* нестабильности
* непредсказуемых результатов

---

## 🔒 1.5 Инварианты трансформации (UPDATED CORE)

1. Все преобразования (до применения Δ) вычисляются относительно **S_real**.
2. Игрок формирует действия на основе **S_perceived**.
3. **Morok искажает восприятие (`S_perceived`) и влияет на параметры вычисления Δ**.
4. **Δ применяется к S_real только один раз (snapshot semantics)**.
5. **Clamp выполняется только в самом конце обновления состояния**.
6. Все функции:

   * детерминированные (при фиксированном seed),
   * непрерывные,
   * без дискретных ветвлений.
7. Нелинейность разрешена:

   * в Morok
   * в Zaryana
   * в функциях стабилизации (при сохранении непрерывности).
8. Состояние всегда удовлетворяет ограничениям:

```text
|d| = 1
0 ≤ m ≤ M_max
```

---

## 🔒 1.6 Приращение состояния (ΔS) (CORE)

Изменение состояния задаётся как:

```text
ΔS = (Δd, Δm)
```

---

### Обновление:

```text
d' = Normalize(d + Δd)
m' = clamp(m + Δm - Decay(m), 0, M_max)
```

---

### Decay (обязательный стабилизатор)

```text
Decay(m) = λ * m
```

---

👉 гарантирует:

* отсутствие бесконечного роста
* устойчивость системы

---

## 🔒 1.7 Роль Morok (UPDATED CORE)

Morok влияет на систему на двух уровнях:

---

### 1. Восприятие

```text
S_perceived = Distort(S_real, Morok)
```

---

### 2. Косвенное влияние на Δ

Morok не искажает Δ напрямую как отдельную фазу,
но влияет на него через:

* искажение входных данных (S_perceived)
* увеличение ошибки намерения (ΔIntent)
* изменение контекста вычисления

---

### Разложение Distort

```text
d_perceived = Normalize(d + Noise(M) + Bias(M))
m_perceived = m * (1 + ε(M))
```

---

## 🔒 1.8 Meta Coupling (уточнение)

Все вычисления Δ выполняются:

```text
из одного snapshot состояния S_real(t)
```

---

Это означает:

* нет последовательного “накопления внутри шага”
* нет зависимости от порядка операций
* система коммутативна в рамках одного тика

---

## 🔒 1.9 Поток данных (FINAL)

```text
Input: S_real(t)

→ Distort → S_perceived
→ Player Action
→ Intent_player
→ Intent_system (через S_real)
→ Compute ΔS
→ Apply ΔS
→ Clamp / Normalize
→ Output: S_real(t+1)
```
