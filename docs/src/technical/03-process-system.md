# 3. СЛОЙ ПРЕОБРАЗОВАНИЯ (PROCESS SYSTEM)

## Process System как динамическая система (каноническое описание)

**Process System** представляет собой детерминированную вычислительную систему,
в которой входное состояние преобразуется в выходное через фиксированный пайплайн.

Обратная связь через Memory System существует между вызовами,
но не внутри одного выполнения Process System.

Формально:

1. Приращение Δ формируется на основе last_distortion из Memory System, а не текущего distortion состояния.
2. Morok нелинейно искажает Δ (но не само состояние).
3. Искажённое приращение Δ_morok добавляется к текущему состоянию.
4. Stability управляет коллапсом: при падении ниже порога состояние плавно деградирует (Collapse).
5. Zaryana не уничтожает, а структурирует результат через интерполяцию между искажённым состоянием и его структурированной формой ψ(S).
6. Memory System сохраняет last_distortion, замыкая петлю обратной связи для будущих итераций.

Ключевые свойства: детерминизм, непрерывность, отсутствие ветвлений, замкнутость.

---

## Определение состояния и шага преобразования

Система рассматривается как одношаговое преобразование без внутренней итерации:

`S_out = Process(S_in, context, modifiers)`

где:
S_in – входной вектор (axes, meta без distortion) после Input Assembly;
S_out – результирующий вектор (axes, meta c distortion);
Δ вычисляется внутри Process System как вспомогательная величина и не сохраняется между вызовами.

Динамика во времени (эволюция мира, обновление памяти) происходит между вызовами Process System, а не внутри него. Это гарантирует детерминизм, отсутствие скрытых состояний и лёгкость тестирования.

---

## 3.1 Система обработки (Process System)

**Process System** — единый слой, в котором выполняются все преобразования параметров.

**Вход**: GameplayParams (axes, meta, modifiers, context)
**Выход**: Result Vector (axes, meta + distortion)

**Process является бинарным композиционным оператором** над (State, Ingredient). Он детерминирован, не имеет состояния между вызовами, но **зависит от порядка применения** (некоммутативен).

**partial_process** — редуцированная версия Process System, используемая в fold.

Она включает следующие этапы:

* Aggregation Refinement
* Context Modifiers
* Water Application
* Axis Sign Modifiers
* Interaction Rules

Она НЕ включает:

* Δ Calculation
* Morok
* Conflict Resolution
* Collapse
* Zaryana

Таким образом, **partial_process формирует состояние S, полностью пригодное для вычисления Δ, но не содержит distortion и не включает нелинейные этапы**.

Характеристики:

* отсутствуют ветвления (if/else)
* все операции детерминированы
* преобразования выполняются последовательно

Порядок обработки фиксирован и не изменяется.

---

## 3.2 Уточнение агрегации (Aggregation Refinement)

На этом этапе агрегированные входные значения преобразуются в начальное состояние для динамики процесса.

### Основная операция

Для каждой оси:

`axis = axis × potency`

### Применение к мета-параметрам

Aggregation Refinement применяется **только к осям (axes)**. Мета-параметры (potency, purity, stability, resonance, corruption) на этом этапе **не изменяются**.

Обоснование: Мета-параметры описывают свойства состояния, а не направленность. Их трансформация происходит на следующих этапах (Context Modifiers, Interaction Rules, Morok).

### Свойства этапа

* все операции линейны
* не используется clamp
* результат может выходить за пределы [-1,1]
* создаётся начальное состояние S₀ для Process System

---

## Определение приращения Δ

Δ вычисляется на основе состояния **S_final_before_morok**
(то есть после всех этапов partial_process).

После завершения формирования состояния S (включая последовательную агрегацию, если она используется) вычисляется приращение Δ. Aggregation Refinement влияет на Δ косвенно, так как участвует в формировании S_final_before_morok, но окончательное вычисление Δ выполняется один раз — после завершения fold.

S_final_before_morok — это состояние после завершения:

* fold (если есть)
* всех этапов partial_process

Именно это состояние используется как S_old в Morok.

---

### Базовые компоненты

Для осей:

`Δ_axes = axes × potency × K_AXIS_GAIN`

Для мета-параметров:

`Δ_meta = (meta - 0.5) × potency × K_META_GAIN`

Применяется к: potency, purity, stability, resonance, corruption. `distortion` не участвует.

---

### Bootstrap-компонента

`Δ_bootstrap = κ × last_distortion`

Применяется с учётом направления:

`Δ_axes_total = Δ_axes + sign(axes) × Δ_bootstrap`
`Δ_meta_total = Δ_meta + sign(meta - 0.5) × Δ_bootstrap`

где sign(0) = 0, знак определяет направление усиления.

---

### Итоговое приращение

`Δ = (Δ_axes_total, Δ_meta_total)`

---

### Свойства Δ

* Δ не является частью состояния (не входит в Vector)
* Δ не сохраняется между вызовами Process System
* Δ может принимать любые значения (не ограничен диапазоном)
* Δ не нормализуется перед Morok

---

### Динамическая устойчивость

Bootstrap создаёт положительную обратную связь: при росте distortion усиливается Δ, что может приводить к ускоренной деградации состояния. Рекомендуется `κ ≤ 0.1`.

---

### Инварианты этапа

* Δ вычисляется строго один раз
* Δ используется только в Morok
* Δ не влияет на состояние напрямую (только через Δ_morok)
* отсутствуют нелинейные преобразования

---

## 3.3 Контекстные модификаторы (Context Modifiers)

### Pressure

**Pressure** — производный параметр, вычисляемый из модификаторов входа. Он не связан с временем или температурой.

Формально:

`pressure = f(intensity, method, disturbance)`

Pressure влияет на:

* Morok (усиление искажения)
* Conflict Resolution (через stability_eff)

Pressure не является частью состояния и не сохраняется между вызовами.

Перед использованием в Process System pressure нормализуется в диапазон `[0, 1]`.

---

### Применение коэффициентов

Контекст преобразуется в коэффициенты `k_axis_total` и `k_meta_total` (см. раздел 5) и применяется к состоянию мультипликативно:

`axes = axes × k_axis_total`
`meta = meta × k_meta_total`

---

### Ограничения

* Для **meta**: если `k_meta_total < 0`, то `k_meta_total = 0`
* Для **axes**: отрицательные значения `k_axis_total` допустимы и интерпретируются как инверсия осей
* clamp не применяется
* значения могут выходить за диапазоны

---

## Применение в пайплайне

Порядок операций строго фиксирован:

1. Context Modifiers (мультипликативно)
2. Water Application (аддитивно)
3. Axis Sign Modifiers (непрерывные модификаторы)
4. Interaction Rules

Все операции выполняются без clamp.

---

## Water Application (формализация)

После применения контекста добавляются модификаторы выбранной воды.

Для осей:

for each ax in {body, mind, spirit, nature}:
axes[ax] = axes[ax] + Δax

Для meta:

for each m in {potency, purity, stability, corruption}:
meta[m] = meta[m] + Δm

---

### Ограничения Water Application

* `resonance` не изменяется водой напрямую
* `distortion` не изменяется водой
* значения могут выходить за допустимые диапазоны
* clamp отсутствует

## Ограничения использования clamp

В системе допускается использование clamp **только в следующих местах**:

* вычисление `λ_raw`
* вычисление `λ`
* вычисление `collapse_factor`

Во всех остальных этапах clamp запрещён.

## 3.6 Разрешение конфликтов (Conflict Resolution)

### Эффективная стабильность

где:

* pressure предварительно нормализован в диапазон [0,1]
* `CR_PRESSURE_STABILITY_FACTOR` — конфигурационная константа

## 3.7 Ограничения идентичности (Заряна / Zaryana)

### Коэффициент структурирования

`Z = (1 - distortion) × (1 - K_ZARYANA_CORR × |corruption - 0.5|)`

Z не ограничивается clamp, однако конфигурация параметров должна гарантировать, что Z остаётся в диапазоне [0,1]. Выход Z за пределы диапазона считается некорректной конфигурацией системы.
